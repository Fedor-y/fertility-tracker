### Реализованные правила и связь с ТЗ

- **ТЗ §2, §9, §11 / ANA-01–03.** Сохранён единственный прежний расчёт индекса; три числовых нуля дают 0, любой специальный ответ исключает индекс, но числовые компоненты участвуют в собственной статистике. Не заполненные поля не создаются. Совпадающие моменты не удаляются и не усредняются до дневной агрегации. Физическое состояние и настроение имеют независимые дневные значения и сводки; стресс не получает дневной сводки.
- **ТЗ §11 / ANA-01–02.** Дневная медиана использует все подходящие числовые наблюдения даты, одна запись допустима. Сводка — медиана дневных медиан, среднее дневных медиан, минимум/максимум именно дневных медиан со всеми датами. До 7 подходящих дат summary=None, но дневные значения, объём и покрытие доступны. Производные значения не округляются; округление относится к будущему отображению.
- **ТЗ §10–11 / ANA-03, ANA-06.** DateRange включает обе даты. Покрытие хранит числитель/знаменатель и неокруглённый процент. Полные месяц/год не обрезаются сегодняшней датой; будущие даты пусты, остаются в календарном размере и не создают наблюдений. Моментальный ввод после context.now не участвует в расчёте даже в пределах сегодняшней даты. Текущий незавершённый день также помечает период неполным. Отсутствие пригодных данных не создаёт нулевых сводок.
- **ТЗ §11 / ANA-06.** Автосравнения предусмотренных ТЗ недели/месяца используют одинаковую прошедшую календарную часть, неделя с понедельника, предыдущий месяц ограничен его последней датой. Два произвольных диапазона задаются явно, могут иметь разную длину и пересекаться. Разница — первая медиана сводки минус вторая, в пунктах; при недостатке дней у любого периода — None. Дополнительный отдельный автоматический режим сравнения лет не вводился; год доступен как полный быстрый или явный диапазон, как предусмотрено §10–11.
- **ТЗ §6, §9, §11 / ANA-04.** Сон группируется по местному пробуждению, длительность — из UTC. Используется обычная дневная медиана индекса; нет альтернативного пересчёта. Даты без сна/медианы, с несколькими снами и с полным когнитивным часом, начавшимся до единственного пробуждения, исключаются. Начало ровно в пробуждение допустимо; ранний неполный индекс не исключает дату. Причины возвращаются по датам, число исключённых дат не удваивается. При нескольких снах дата уже исключена как неоднозначная, выбор одного «основного» пробуждения не производится.
- **ТЗ §8, §11 / ANA-05.** Только явные Был/Не был и даты с дневной когнитивной медианой; неизвестность не становится отрицательной отметкой. Возвращаются дневные точки, медианы и числа дат групп; при <5 дат в любой группе — «Мало наблюдений для сравнения», вычисления не блокируются. Пустая группа имеет median=None, difference=None. Разница подписана как Был минус Не был. Сложность сохранена в данных точки и не используется для группировки. Дополнительного порога 7 дней для факторов нет.
- **ТЗ §9, §11, архитектура / READ-01 и основа READ-02.** Контекст содержит один явно переданный UTC-момент и пояс. Application читает все семь прежних репозиториев через один read_snapshot, передаёт Domain только неизменяемые модели, закрывает транзакцию до вычислений. AnalyticsSnapshot сохраняет ID и исходные версии. Неизвестная шкала/формула вызывает явную ошибку, не подменяется версией 1. SnapshotToken позволяет проверить поколение/идентичность базы; контроллер запросов и применение в графике относятся к следующей порции и не реализованы.

Проверка параллельной записи управляется Event, без надежды на случайный порядок: читатель фиксирует когнитивные данные, другой поток правит настроение и удаляет зал, читатель получает согласованное прежнее состояние всех журналов, после закрытия снимка commit завершается и прежний токен становится неактуальным. ### Потоки, ошибки и жизненный цикл

- ChartRequests владеет ThreadPoolExecutor с двумя рабочими потоками. Параметры запросов и результаты неизменяемы; общий Storage — прежний потокобезопасный координатор, а не общее SQLite-соединение. Каждый worker читает своим соединением, Session остаётся внутри load.
- При новом запросе/инвалидации отменяются ожидающие задачи; выполняющаяся работа проверяет отмену между безопасными фазами. Нельзя принудительно оборвать SQLite или расчёт. Выполнившаяся вопреки отмене задача всё равно обязана пройти проверку ID/токена.
- Callback worker кладёт типизированный ChartOutcome в очередь, не вызывает Qt. Qt-адаптер получает данные QTimer в потоке владельца. Никаких случайных задержек/sleep для согласования порядка тестов не используется: порядок задают Event и completion callbacks/futures.
- Storage.capture_token вызывается рабочим потоком, включая привязку ошибок загрузки; после загрузки используется токен прочитанного снимка. Storage.apply_if_current не ждёт занятый замок (None), отвергает устаревший токен (False) либо выполняет короткий callback атомарно относительно commit (True). Для данных база должна быть открытой/исправной; ошибка текущего запроса может сообщить о недоступности, оставаясь привязанной к идентичности/поколению.
- Callback применения не должен выполнять SQL, тяжёлые расчёты или запускать вложенный event loop. result_ready — уведомление, не право сохранить данные и позже применить их без проверки; для позднего потребителя предусмотрен ChartController.deliver, повторяющий проверки. Последнее хорошее состояние хранится отдельно от текущей ошибки.
- Ошибки Storage/Domain и неожиданной подготовки возвращаются с безопасными кодом/текстом; исходное сообщение исключения не передаётся Presentation и не журналируется. Устаревшие ошибки не заменяют новое состояние.
- MainWindow инвалидирует запрос после успешной правки/удаления. Закрытие запрещает новые запросы и остаётся неблокирующим, пока активные работы безопасно заканчиваются, затем закрывает базу. При отказе закрытия хранилища приём запросов возобновляется. aboutToQuit/уничтожение QObject и finally bootstrap управляемо завершают пул до закрытия хранилища; штатный выход и исключение из event loop завершают собственные рабочие задачи до закрытия хранилища.

### Механизм и граница гарантии

- `ChartPayload` — frozen-модель конверта: версия протокола 1, page/request/delivery ID, возрастающий sequence, подготовленные данные. В данные входят режим, диапазон/контекст, точки/сегменты, определения/версии, исходные когнитивные ответы и ссылки на записи, календарные события и сон. Это JSON, без Python-объектов, SQL, HTML, кода и ECharts option. Вычисления и сегментация прежние, не перенесены в JS. Ноль, null и два специальных статуса сохраняются.
- Готовность ECharts 6.0.0 и WebChannel отделена от передачи/принятия данных. Handshake проверяет экземпляр страницы и версию библиотеки; число наблюдений не является условием готовности. Автоматического запроса данных при запуске нет.
- Сериализация выполняется после возвращения из callback контроллера. Непосредственно перед `payload.emit` вызывается прежний `ChartController.deliver`, который проверяет request ID, SnapshotToken и пояс через неблокирующий `apply_if_current`. Никаких новых mutex, портов или механизмов блокировки записи не потребовалось; **application/storage.py и infrastructure/sqlite/database.py не изменены**.
- JS проверяет конверт/структуру данных, сохраняет снимок **предварительно**, затем отправляет `received(page, request, delivery)`. Python повторяет guard и только после успеха принимает снимок, посылая `confirmed`. Это означает актуальность **на момент проверки**, не обещание будущей актуальности и не подтверждение отрисовки реальных серий. JS после ответа тоже хранит только протокольное состояние.
- Новый запрос/отмена/начало закрытия инвалидируют прежнюю доставку. Новая доставка заменяет предыдущую; старая страница, ID и последовательность не могут подтвердить новую. Прежние подтверждения/ошибки игнорируются. JS отбрасывает задержанные данные/confirmed после сообщения инвалидации.
- После принятия bridge проверяет актуальность каждые 25 мс при работающем GUI. Смена поколения/идентичности базы даёт `stale`; смена запроса/пояса также инвалидируется контроллером. Занятый координатор даёт `updating/checking`, без заявления актуальности и без ожидания замка. Это частота опроса, а не гарантированное время реакции ОС или зависшего renderer.
- Доставка ограничена 5 секундами монотонного времени, включая отложенную отправку и проверку ответа. Срок проверяется также непосредственно при `received`, чтобы поздний ответ не опередил QTimer. Истёкший снимок старого поколения даёт устаревание, а не ошибку актуальных данных. Во время ожидания нет SQLite-сессии, замка или запрета commit. Повторы ограничены сроком доставки; после отказа доступен новый запрос с новым ID и актуальным контекстом.
- `loadStarted` меняет page ID и сбрасывает готовность; новая страница проходит handshake и может получить ещё актуальный готовый результат. Старые hello/подтверждения/ошибки не влияют на неё. Начало закрытия сразу закрывает мост; поздние события не открывают его заново. При отказе закрытия базы канал может возобновиться вместе с контроллером.
- Состояния интерфейса различают готовность, передачу, предварительный приём, проверенное принятие, обновление, устаревание и ошибку. Кнопка повторяет только ранее существовавший запрос. JS выводит состояния через `textContent`; значения пока не рисуются.

Оставшаяся асинхронная граница обозначена явно: commit может произойти после проверки Python и до получения JS сообщения `confirmed`. JS временно может хранить предварительный или уже проверенный старый снимок. Инвалидация доводится позже; native UI при обнаружении показывает устаревание/обновление. Это согласованная eventual consistency, **не** строгая атомарность двух процессов. При зависшем renderer native UI продолжает работать; не заявляется возможность немедленно изменить DOM зависшего процесса.

### Что отображается

- Семь поддержанных рядов: индекс, запоминание нового, воспроизведение и применение, скорость мышления, физическое состояние, настроение, стресс. Ноль остаётся числом; специальные ответы не получают координату Y=0, доступны как текстовые наблюдения в коротких временных режимах.
- DAY: реальная длительность местных суток, включая 23/25 часов; COMPACT: равные календарные полосы 00–24; TIMELINE: непрерывное реально прошедшее время; DAILY: прежние независимые дневные медианы. Порог выбора режимов прежний: 1, 2–7, более 7 дат. Масштаб оси не пересчитывает статистику.

Полоса делится у календарных границ и изменений смещения при COMPACT/DAILY, не рисуя обратный ход через повторный час. Отбор сна по дате пробуждения остаётся прежним, основным источником остаётся AnalyticsSnapshot.

CalendarEvent расширен необязательными attended/difficulty из прежней модели зала: явное «Не был» отличается от отсутствия карточки; при «Был» доступна сложность, включая 0. ### Архитектура и протокол

`application/chart_projection.py` преобразует PreparedChart в координаты, подписи и тексты без повторного расчёта индекса, медиан или сегментов. ChartPreparation готовит проекцию в worker после закрытия SQLite-сессии; ChartResult хранит её неизменяемой JSON-строкой. ChartPayload добавляет поле view, сохраняя исходные поля контракта версии 1. При ручном использовании фабрики без готовой проекции оставлена совместимая подготовка по PreparedChart; рабочий путь приложения использует готовую строку worker.

Точные моменты проецируются в секунды относительно реального начала диапазона, без обрезания микросекунд до Unix-миллисекунд. Календарные дневные позиции — позиции столбцов дат, не выдуманные времена измерений. Подписи времени/даты и особые статусы готовит Python. JS выполняет только сборку ECharts series, геометрию прямоугольников, отображение DOM и взаимодействие.

`chart_render.js` отделяет визуализацию от протокола. Предварительный пакет не меняет рисунок: setOption вызывается только после подходящего confirmed. Старый рисунок при stale/checking/error остаётся приглушённым с явным предупреждением; при ошибке построения нового view прежний успешный рисунок сохраняется. При настоящем падении renderer само изображение, конечно, теряется; native UI показывает ошибку, SQLite продолжает работать. Кнопка повтора распознаёт потерю renderer, выполняет reload и новый запрос. Новый page ID и все прежние проверки запроса/доставки/токена/пояса сохраняются.

Обратный контракт openSource принимает page/request/delivery ID, известный тип и десятичный ID. Источник должен входить в whitelist именно текущей доставки; перед действием повторяется guard. Сигнал открытия испускается **после освобождения guard**, поскольку существующая форма читает SQLite. SQL/диалог не исполняются внутри короткого атомарного участка.

ResizeObserver согласует canvas с реальным размером контейнера, в том числе после появления карточек и полосы прокрутки. При коротком окне/200% используется вертикальная прокрутка и минимальная высота графика 400 логических пикселей. Легенда прокручивается, не переключает фильтры. Минимальная высота числовой координатной области с полосой сна проверяется отдельно (не менее 150 логических пикселей).

Единственный допустимый режим показан, но переключатель отключён. Предпочтение COMPACT/TIMELINE сохраняется при переходах через DAY/DAILY; ряды, слои и порог линий не сбрасываются.

Индивидуальные флажки питания/зала сохраняются при выключении общего. Сон управляется отдельно. Все слои меняют только представление; аналитика считается по прежнему полному снимку.

- Смена даты/часового пояса обнаруживается Qt-таймером раз в секунду при работающем GUI. Быстрый период пересчитывается в новом AnalysisContext; явный диапазон сохраняется. Старый запрос инвалидируется, создаётся новый. Ошибка неверного диапазона не маскируется состоянием загрузки после смены контекста. Это интервал опроса, не гарантия предельной задержки ОС.

Ошибки чтения/подготовки и reload не сбрасывают выбранные параметры. Повтор использует текущую панель; для отдельного программного ChartQuery без участия панели сохранена совместимость прежнего пути.

Панель Qt компактна: основная строка периода/режима, раскрываемые «Ряды и слои», прокрутка длинного списка, адаптация в одну/две колонки, видимый фокус клавиатуры и небольшие оранжевые акценты. Семь форм/дневник не менялись. JavaScript обслуживает отрисовку и жесты ECharts; выбор календарных диапазонов/режима и построение ChartQuery остаются на Python-стороне. ### Потоки и согласованность

Каждое изменение периода, режима, ряда или слоя создаёт новый frozen ChartQuery и UUID через существующий ChartController/ChartRequests. Новые show_sleep/show_meals/show_gym/show_events — строго bool, без SQLite-полей. SnapshotToken и весь протокол page/request/delivery/sequence сохранены. UI не ждёт SQLite и не выполняет SQL: чтение и подготовка остаются в worker. Отмена старой работы не заменяет проверку ID/токена.

Application сначала рассчитывает analytics по полному AnalyticsSnapshot, затем формирует видимые серии/слои. show_events меняет только подготовленное view. Временные границы/календарные преобразования и статистика не перенесены в JS. Смена видимости не пишет в базу, не меняет наблюдения и не меняет расчётную аналитику того же диапазона/контекста.

Сохраняется согласованная eventual consistency, не строгая атомарность Python/JS: предварительный пакет не рисуется, подтверждение относится к моменту проверки, после изменений прежний рисунок явно устаревает. Перезагрузка страницы сохраняет native Qt-панель; прежние проверки доставки повторяются. Закрытие и работа с погибшим renderer покрыты прежними тестами в полном наборе.

### Реализация и архитектура

AnalyticsPagePreparation и AnalyticsQuery используют существующий Analytics, расширяя только сценарий страницы. Границы выбранного и сравниваемых периодов объединяются для одного Analytics.load; после закрытия сессии выбираются нужные записи и вызываются прежние calculate_snapshot/period_statistics/compare_periods. ChartPreparation.prepare_snapshot переиспользует прежнюю подготовку; дневной режим Аналитики отделён от неизменных правил DAY/COMPACT/TIMELINE/DAILY Обзора. AnalyticsView содержит готовые строки/точки для Qt и ECharts. Выбранный уже рассчитанный PeriodStatistics повторно не вычисляется.

Новая AnalyticsPage создаёт собственный экземпляр прежнего ChartController/ChartRequests и локальный ChartView только при первом открытии. Это тот же Storage/ApplicationSession, собственное соединение каждого worker и прежние UUID/отмена/токены/пояс. Скрытая страница инвалидируется, при возвращении запрашивает новый снимок. Таймер контекста обновляет дату/пояс. После сохранения наблюдений или предпочтений активная страница обновляется.

Сводки шести показателей, дневная таблица и сравнения доступны на трёх вкладках. Полные даты экстремумов прокручиваются в read-only QPlainTextEdit. Таблицы используют ленивый QAbstractTableModel с уже подготовленными строками; SQL/расчётов в виджетах нет. Дерево Qt строится вне guard; перед короткой заменой повторно вызывается ChartController.deliver. Старое дерево сохраняется с явным состоянием устаревания/ошибки. Занятый координатор откладывает публикацию, GUI не ждёт блокировку.

Для всех шести Indicator доступны дневная таблица и сравнения. В существующий analytics_indicator запоминаются только индекс и три компонента. Выбор физического состояния/настроения действует в текущем сеансе и явно описан в tooltip. Новых полей/enum хранения нет, модель ChartPreferences/SettingsRepository не расширялась. Периоды, сравнения, вкладки и zoom не сохраняются. Ряды/слои/compact_mode синхронизированы с прежними предпочтениями Обзора; статистика не зависит от скрытия графики.

В существующем chart_render.js добавлены два scatter-grid, получающие готовые Python-точки факторов. Нет регрессии/прогнозной линии и JS-статистики. Базовый дневной график сохраняет источники, версии и прежние специальные ответы. Поле view.factors — обратно совместимое расширение проекции, версия WebChannel 1 и последовательность provisional/received/confirmed прежние. Данные рисуются после confirmed; eventual consistency не называется строгой атомарностью. При ошибочном factors прежний ECharts option остаётся, показывается ошибка.
