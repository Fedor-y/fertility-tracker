## Реализовано

- AccessState NORMAL/EXCLUSIVE/RECOVERY_REQUIRED и неизменяемый AccessStatus в порте
  Application; отдельная закрытость, без четвёртого режима доступа.
- Допуск сессий через Condition, активный счётчик до открытия/после закрытия
  соединений. Прежний RLock продолжает защищать SQL-запись и токены.
- Database.exclusive(cancel=Event): запрет новых сессий, ожидание принятых запросов,
  сериализация конкурентов, отмена ожидания, удержание прежнего flock.
- Потоковое разрешение confirm_safe с read-only проверкой SQLite/FK/полной схемы.
  Без подтверждения или при исключении — RECOVERY_REQUIRED. Ошибка действующей
  сессии во время ожидания не снимается.
- verify_access для явной проверки при удерживаемой блокировке экземпляра.
  Успех инвалидирует старые токены через новый UUID. UI не подтверждает безопасность.
- ApplicationSession получает доступность напрямую из Storage.access_status;
  кэш флага удалён. MainWindow обновляет действия и сообщение существующим таймером.
- close запрещён при активных сессиях/exclusive. Ошибка освобождения flock
  блокирует доступ и повторное закрытие потенциально переиспользованного fd.

Ожидание Condition освобождает gate, SQL RLock при ожидании не удерживается.
Если нужны оба замка, порядок RLock → gate. Под gate не ждут RLock/worker.
Существующий closeEvent/bootstrap не переставлялся; worker защиты ещё не создавался.

## Механизм и согласованность

Infrastructure SQLiteBackup получает явный BackupRequest и создаёт снимок через
sqlite3.Connection.backup, без shutil/copyfile. После допуска exclusive все прежние
читатели/писатели завершены. ExclusivePermission.token захвачен после дренирования;
commit до его фиксации включён, новые сессии/commit во время снимка запрещены.
confirm_safe(unchanged=True) проверяет источник и сохраняет прежний токен, только
для этого read-only сценария. Default поведения части 1 не изменён. При ошибке носителя
источник повторно проверяется и остаётся NORMAL, если исправен. Повреждённый/неизвестный
источник остаётся RECOVERY_REQUIRED. Ошибки не обходят MigrationBackupRequired.

Страницы копируются блоками по 128, прогресс передаёт remaining/total; монотонный
тайм-аут API — 30 секунд. Соединения открываются/закрываются в том же worker.
После Backup API соединения закрыты, источник проверен, exclusive освобождён.
Целевая проверка/публикация идут без запрета сессий; более поздние изменения источника
не считаются защищёнными. Обычные read_snapshot/write и Domain не переписывались.

## Проверка и метаданные

Проверяется фактическое открытие SQLite, integrity_check, foreign_key_check,
полная ожидаемая схема (таблицы, индексы, триггеры), история/контрольные суммы
миграций. Типизированный неизменяемый BackupMetadata содержит:
ID, UTC, архивную дату, SnapshotToken источника, версию схемы, checksum миграции,
BackupKind, размер, SHA-256 файла, verified=true и версию формата.
JSON дополнительно содержит magic-format и checksum канонической записи метаданных.
Поля/типы/повторяющиеся ключи/форматы валидируются; JSON не больше 64 КиБ.
После записи метаданные снова читаются, сопоставляются с копией; схема и SHA проверяются
повторно. inspect_backup выполняет независимую проверку опубликованного пакета,
в том числе после повторного открытия приложения. Имя файла/каталога недостаточно.

## Публикация и отказы

Пакет — приватный каталог с database.sqlite3 и metadata.json. Временный .pending
создаётся в целевом каталоге. Только после проверки и fsync файлов/временного каталога
пакет атомарно переименовывается renameat2(RENAME_NOREPLACE), затем fsync родителя.
Существующее имя (включая пустой каталог и symlink) не перезаписывается. Пути обходятся
через fd с O_NOFOLLOW; конечные каталоги/файлы только владельцу, новые 0700/0600,
hardlink файлов не допускается. Нет небезопасного fallback при отсутствии поддержки.

ENOSPC/EACCES/EIO, отказ Backup API, записи, fsync, переименования и проверки дают
BackupError без личного содержимого. Удаляются только новые файлы текущей операции;
старые копии не удаляются для освобождения места. Если сам носитель не допускает
очистки, pending может остаться; он не принимается как пригодный. Автоматической
уборки старых pending/архива в этой части нет.

## Application и закрытие

BackupService — одна последовательная очередь всех типов, Future и типизированный
прогресс, вне GUI. Путь передаётся явно, QSettings/страница/кнопки не добавлены.
Event отменяет до входа в критическую последовательность. После начала Backup API
Event не объявляет безопасную отмену. Отменённый до запуска Future не теряет счётчик
pending и не мешает закрытию. Нет новых соединений, передаваемых между потоками.

ApplicationSession.close отказывается закрывать базу до завершения всей задачи,
включая публикацию при уже NORMAL источнике. MainWindow ждёт через event loop перед
финальным flush, затем прежняя цепочка контроллеров/задач/хранилища; bootstrap finally
дожидается backup worker. Новых пользовательских элементов нет, автоматического запуска
копирования при обычном открытии приложения нет.

# Этап 6, часть 4 — базовое восстановление

Новое прямое задание. Исходная точка — 1154 passed / 7 warnings.

## Что реализовано

На странице Настройки → Резервные копии выберите строку, нажмите «Восстановить» и
подтвердите предупреждение с датой, размером и статусом. Отказ выбран по умолчанию.
Выбранный пакет повторно проверяется inspect_backup. Независимый кандидат готовится
на файловой системе основной базы, сверяется с BackupMetadata (размер/SHA) и проходит
проверки SQLite, FK и полной известной схемы/истории миграций.

Отдельный Application-сценарий Restoration выполняет это в прежней очереди worker.
Перед заменой прежний BackupService создаёт полноценную проверенную копию текущего
состояния через Backup API, формат тот же, тип PRE_RESTORE. submit/result в собственный
пул не используется. BackupMetadata/формат пакета не изменялись.

Затем Database.exclusive ждёт все сессии, удерживает flock, сравнивает токен с новой
защитной копией. Commit в промежутке отменяет замену, а не теряет незащищённую запись.
Проверочное соединение источника закрывается до перемещения файлов. Основной SQLite
и имеющиеся WAL/SHM/journal сохраняются в .restore-<UUID> рядом с базой. Кандидат
заменяет рабочий файл, выполняются fsync, повторное открытие, SQLite/FK/структура.
Успех меняет UUID/поколение и требует нового запуска.

В интерфейсе показаны результат и расположение защитной копии, кнопка «Закрыть для
перезапуска». Она закрывает приложение; пользователь запускает HealthTracker снова.
Старые контроллеры/навигация не используют восстановленные данные до перезапуска.
Настройки окна/каталога QSettings не заменяются. Настройки application_settings
восстанавливаются вместе с SQLite и загружаются при новом открытии.

## Отказы и прерывание

Копия с неверными метаданными/хешем/FK/неизвестной схемой отклоняется до замены.
Ошибка создания защитной копии оставляет текущую базу доступной, замена не начинается.
При обычном отказе после перемещения возвращается исходный комплект и проверяется;
после такого отката также нужен перезапуск. Повреждённый новый файл сохраняется
отдельно, исходные/защитные файлы не удаляются.

Перед перемещениями fsync-ится небольшой <database>.restore-pending. Он удаляется
после успешных проверок. Если последний fsync после unlink отказал, до отката снова
ставится маркер. При неопределённости работа блокируется, самопроизвольного возврата
к NORMAL нет. Следующий initialize сначала получает прежний flock и проверяет
маркер, затем допускает создание отсутствующей базы: незавершённая замена не
подменяется пустым файлом. Автоматического разбора/продолжения маркера нет.

MainWindow перед worker дописывает предпочтения и завершает контроллеры; сохранение
их старого состояния после замены не допускается. Close во время подготовки ждёт
её отправки, close во время worker ждёт завершения. GUI не делает join/result
незавершённого Future, SQLite-соединения не передаются между потоками. Новый флаг
AccessStatus.restart_required не добавляет четвёртый AccessState.
