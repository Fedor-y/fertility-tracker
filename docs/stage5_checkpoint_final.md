Этапы 1–3 завершены; этап 4 технически принят с прежними ограничениями ручной приёмки. Пользовательский объём этапа 5 реализован в порциях 1–3 и частях 1–5 порции 4. Отдельная порция 5 плана не начиналась. Следующего разрешения на реализацию нет; этап 6 запрещён.

## 3. Обзор

Реальные графики ECharts 6.0.0, семь рядов, четыре режима, быстрые/явные включительные периоды, слои, подсказки и открытие прежних форм по источникам. Нули/специальные ответы/совпадающие UTC/исторические версии/DST сохраняются. Краткая статистика готовится worker, показывает покрытие, объём, порог 7, M/A/min/max и неполноту; устаревшее состояние помечено.

## 4. Аналитика

Вместо заглушки — AnalyticsPage. Доступны прежние быстрые периоды плюс текущая неделя до сегодня через comparison_periods(WEEK). Три вкладки: сводки шести Indicator, дневные значения выбранного, сравнения и факторы. Полные даты экстремумов выбранной строки — read-only прокручиваемый plain text. Сравнения текущих недель/месяцев используют одинаковую прошедшую календарную часть Domain; произвольная пара задаётся четырьмя календарями. Разница только в пунктах и только при обеих сводках.

Динамика — дневной ECharts; стресс остаётся исходными маркерами. Сон — scatter UTC-часы/обычная дневная медиана индекса, все причины исключения и число дат. Зал — дневные точки по явным Был/Не был, размеры/медианы/разница, предупреждение при <5 в любой группе; пустая группа не получает ноль. Сложность только в tooltip. Новых факторов/корреляций нет.

## 5. Domain и один снимок

Domain.analytics/periods/factors/charts и версии формул/шкал не менялись. AnalyticsPagePreparation объединяет границы основного и сравниваемых периодов для одного Analytics.load, закрывает сессию, выбирает нужную часть неизменяемых данных и вызывает прежние функции. ChartPreparation.prepare_snapshot переиспользует прежние серии/проекцию; новая логика не вычисляет медианы или индекс самостоятельно.

## 7. Presentation и ресурсы

presentation/analytics_page.py — ленивый ChartView/прежний ChartController, AnalyticsControls, AnalyticsSections/TextTable, публикация Qt через повторный deliver. MainWindow связывает навигацию, общие предпочтения, обновление и закрытие двух страниц. bootstrap завершает оба контроллера до базы. ChartControls.period_for выделен для делегирования выбора недели, без календарных расчётов в Qt.

chart_render.js принимает необязательные view.factors и рисует два дополнительных scatter-grid, без статистики/регрессии/сегментации в JS. CSS даёт читаемую высоту и прокрутку. chart_payload.py/ChartBridge используют заранее подготовленную JSON-часть, добавляют актуальные ID. index.html/CSP, локальная библиотека и ограничения сети не менялись. Открытие источника не сужает ID до Qt int32 (проверен 2^40); прежний JS-предел Number.isSafeInteger остаётся.

## 8. Предпочтения и источник истины

Существующий src/healthtracker/infrastructure/sqlite/settings.py, SettingsRepository.get/set/delete через Session.settings и application_settings. Схема/CHECK прежние. ChartPreferences: visible_series семи SeriesKind, compact_mode, line_gap_hours, analytics_indicator (только cognitive/learning/application/speed), show_sleep/show_meals/show_gym/show_events. JSON ensure_ascii=False/allow_nan=False. Отсутствующие поля получают defaults, False/[] сохраняются. Ошибки/повреждение не уничтожают старые значения; неизвестные строки остаются. Баннер ошибки/повтор общие и видимы на обеих страницах; во время повторного чтения параметры отключены.

Выбор физического состояния/настроения для таблицы/сравнения — только текущий сеанс: новый enum хранения не вводился, это явно указано в tooltip. Индекс/компоненты сохраняются прежним analytics_indicator. Ряды/слои/compact_mode общие для обеих страниц; периоды, сравнения, вкладки, zoom и transport-состояния не сохраняются. QSettings — только окно. Последовательность/debounce/закрытие PreferencesController сохранены.

## 9. Запуск и первоначальные запросы

Bootstrap → ApplicationSession.open → MainWindow. Предпочтения читаются асинхронно до первого Query. Обзор ждёт настройки и ready WebChannel; маркер текущего page ID устраняет гонку двух первоначальных событий. Аналитика создаёт собственный ChartView/экземпляр прежнего ChartController только при первом переходе; один первоначальный запрос. Вновь открытая страница получает актуальный запрос, скрытая инвалидируется. Обычный bootstrap открывает стандартный XDG-путь: в тестах использовать только временные каталоги/базы.

## 10. Актуальность, ошибки и закрытие

Прежние UUID/SnapshotToken/идентичность базы/поколение/пояс/page/request/delivery ID/sequence и provisional/received/confirmed сохранены. Eventual consistency: подтверждение только на момент проверки, не строгая атомарность JS. Смена данных/пояса/запроса инвалидирует прежнее состояние. GUI не ждёт coordinator: готовое дерево Qt строится вне guard, перед коротким показом повторно вызывается deliver; busy откладывает публикацию. Старая ошибка/успех не заменяют новые данные.

Ошибка сохраняет прежнее отображение с предупреждением/повтором. Reload/падение renderer не требуют новых форм или SQL в JS. При close оба bridge запрещают доставку, дописываются предпочтения, затем останавливаются оба контроллера и база. Close во время задачи оставляет GUI работающим; отказ базы допускает возобновление. На выходе event loop bootstrap также завершает оба пула. Блокировка/сессия не удерживаются в ожидании JS.
