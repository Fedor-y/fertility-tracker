## Реализованное хранение

- Один координатор Database: явное initialize, короткие write/read_snapshot-сессии, отдельные соединения в потоках, защита от второго пишущего экземпляра через файловую блокировку.
- Новые файлы 0600 в каталоге владельца 0700. Существующие небезопасные файлы не исправляются молча и не перезаписываются. Вычисление стандартного XDG-пути само по себе ничего не создаёт.
- Foreign keys включены на каждом соединении; synchronous=FULL, стандартное журналирование SQLite. Открытие отсутствующего файла не создаёт базу случайно: создание — отдельное явное действие.
- Полная начальная миграция 0001_initial: 16 таблиц согласно database.md, индексы, FK, CHECK/NOT NULL/UNIQUE, неизменяемые шкалы/формула и фиксированные справочники.
- Первичные ключи наблюдений — INTEGER. Три когнитивных ответа в одной строке. Симптомы, причины и позиции — дочерние строки, не универсальные события.
- Семь репозиториев наблюдений, отдельные репозитории определений и настроек. CRUD не использует автоматический upsert наблюдений. Явная установка настройки может заменить значение того же ключа.
- Результат чтения — StoredRecord с ID и неизменяемой моделью. get отсутствующей записи возвращает None. Исправление/удаление отсутствующей записи сообщает RecordNotFound.
- UTC хранится канонически с шестью цифрами микросекунд. Питание и зал имеют только календарную дату; их время создания не используется как время события. Местная группировка остаётся ответственностью Domain с переданным поясом.

## Целостность и продуктовые правила

- Общая внешняя транзакция объединяет несколько репозиториев. Savepoint защищает каждую составную операцию, не коммитит её отдельно. Ошибка после вставки родителя или первой позиции откатывает все части агрегата.
- Когнитивные специальные статусы сохраняются как отдельные статусы с NULL, ноль — числовым значением. Незаполненные ответы не допускаются. Индекс не хранится как независимая исходная колонка.
- У физических записей сохраняется различие listed/none_confirmed/unknown и необязательная интенсивность каждого симптома.
- Правка положительного стресса в 0 очищает причины и комментарий одной операцией без дополнительного подтверждения. Ошибка очистки откатывает оценку и все связанные изменения. Каталог причин и другие записи остаются.
- Повтор основной категории питания требует duplicate_confirmed=True; иначе ConfirmationRequired без частичного сохранения. Другое не предупреждает. Правка без смены даты/категории не запрашивает подтверждение снова; редактируемая запись исключается из проверки.
- Зал уникален по дате: повторное создание отклоняется, исправление только по ID. Нет строки — неизвестно. При подтверждённом отсутствии сложности нет.
- Пересечения сна проверяются Domain внутри пишущей сессии и дополнительно триггерами SQLite. Касание допустимо. Более 16 часов требует long_sleep_confirmed=True, а не запрещается. Несколько непересекающихся интервалов на дату допустимы.
- Старые определения версий нельзя UPDATE/DELETE. Ссылка на неподходящий код шкалы отклоняется. Неизвестная версия не заменяется текущей даже при попытке исправления записи.
- Удаление родителя каскадно очищает дочерние строки; справочники сохраняются. Подтверждение пользовательского удаления относится к будущему Application/UI, не имитируется в репозитории.

## Миграции и защита границы этапа 4

Migration содержит номер, имя и контрольную сумму. Реестр должен быть последовательным. Новая пустая база получает начальную схему в одной транзакции: DDL, определения, справочники, регистрация schema_migrations. Целостность, foreign_key_check, ожидаемая версия и структура объектов проверяются **до commit**. При ошибке откатываются и таблицы, и данные, и версия. executescript не используется.

Совпадающая существующая схема проверяется read-only и не мигрирует. Неизвестная новая версия, изменённая контрольная сумма, недостающий триггер/индекс или изменённая таблица отклоняются без перезаписывания файла.

Любая ожидающая миграция уже существующей схемы вызывает MigrationBackupRequired. Обходного флага, фиктивного подтверждения копии и реализации Backup API нет. Это предусмотренная граница этапов 3/4: безопасное обновление с реальным защитным снимком реализуется только после отдельного разрешения этапа 4.

Повреждённый файл и неопределённый результат commit/rollback блокируют последующие операции. Исходник не удаляется; пустая база вместо него не создаётся. Восстановление ещё не реализовано.

## Согласованное чтение

read_snapshot фиксирует реальный читающий снимок SQLite и SnapshotToken (идентичность базы и поколение commit) под единым координатором. Все репозитории сессии используют одно соединение и одну транзакцию. Чтение дочерних строк относится к тому же снимку.

При успешной пишущей транзакции поколение меняется; при rollback остаётся прежним. После повторного открытия идентичность меняется даже у того же объекта Database. is_current проверяется после закрытия читающего снимка. Возвращённые модели неизменяемы и могут передаваться будущему расчёту аналитики без соединения SQLite.

Тест с читателем и параллельным писателем подтверждает отсутствие смешанного снимка и последующее отклонение старого токена. Постоянные поколения для резервных копий и интеграция с графиком не реализованы досрочно.
