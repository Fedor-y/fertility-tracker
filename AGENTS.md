## Обязательные технические правила будущей реализации

- Локальное настольное приложение для Arch Linux: Python, PySide6, Qt WebEngine, локальный ECharts, Qt WebChannel, SQLite через sqlite3; без ORM и сервера.
- Четыре слоя: Presentation, Application, Domain, Infrastructure. SQL запрещён в интерфейсе. Все математические расчёты и правила сегментации графика выполняет Python.
- Отсутствие данных, специальные ответы и числовой ноль различаются. Незавершённые когнитивные поля не заполняются автоматически.
- UTC-моменты не подменять временем создания; питание и зал имеют только дату. Исходный часовой пояс события не сохранять.
- Версии шкал и формул неизменяемы; старым записям не назначать новую версию автоматически.
- Составные операции транзакционны. Каждый поток использует своё соединение SQLite. При ошибке форма не теряет ввод, успешное сохранение не имитируется.
- База отдельно от программы; не использовать личную базу в тестах. Миграции требуют проверенной копии до начала и проверок целостности, внешних ключей и версии схемы после применения.
- Копии создавать через SQLite Backup API. Ротация допускается только после успешного создания и проверки нового снимка. Ошибка новой копии не удаляет старые.
- Устаревшие фоновые результаты не должны заменять актуальные данные графика.
- Миграция и регистрация её версии — одна транзакция; проверки до commit, ошибка — rollback. Один расчёт аналитики читает единый снимок и проверяет поколение перед применением.
- Резервирования сериализуются, снимок защищает только зафиксированное поколение. Смена каталога не перемещает/удаляет старые копии. Восстановление требует проверенного кандидата, сохранения исходника и проверки после повторного открытия.
- Проектирование завершено, статус указан в requirements.md, раздел 19. Технические допущения не называть утверждёнными пользователем. Новое существенное противоречие сначала обсуждать.
- Только успешные автоматические копии влияют на автоматическое часовое/дневное расписание; ручные и защитные — нет. При сохранении правки положительного стресса в 0 причины удаляются и комментарий очищается атомарно без дополнительного подтверждения.
- Не отправлять данные в сеть. Не журналировать дневник, оценки, SQL-параметры и сообщения WebChannel. Не добавлять телеметрию.
- QSettings и SQLite имеют разделённые области настроек; не дублировать источники истины.
- Не устанавливать библиотеки в системный Python. Новая зависимость требует конкретного назначения; Pandas и SciPy для MVP не нужны.

## Организация работы после разрешения реализации

Работать небольшими задачами с проверяемым результатом. Перед изменением читать относящиеся к задаче требования. Использовать rg для поиска. Не создавать пустые модули заранее. Не привлекать субагентов без явного разрешения пользователя или применимой инструкции.

Не писать проект огромными кусками. В начале этапа дать короткий план с привязкой к критериям ТЗ, затем выполнять небольшие логически завершённые порции. После каждой порции проверять её и давать промежуточный отчёт: что изменено, какие пункты ТЗ выполнены, результаты проверок и следующий шаг. Пользователь должен иметь возможность сверить работу с ТЗ и скорректировать направление. Не переходить к следующему этапу автоматически; внутри уже разрешённого этапа продолжать работу, учитывая поступающие уточнения.

Добавлять содержательные тесты расчётов, времени, SQLite и отказов вместе с реализацией. Для изменений интерфейса проверять целевой сценарий на Arch Linux. После задачи сообщать, что изменено, как проверено, что осталось и какие есть ограничения. Не заявлять непроведённую проверку.

Фиксация в Git — только после проверки и в пределах разрешения пользователя. Наличие папки .git само по себе не доказывает, что репозиторий инициализирован.
